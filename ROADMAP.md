**The goal:** Nobody should have to think about Minecraft versions or loaders: drop a mod in, as its source folder or as its .jar, from the command line or the desktop app, pick the version and the loader you want, and get it back the same way in minutes, for any mod anyone makes. On the way there: a mod or plugin author never launches Minecraft, a modpack user never diagnoses a conflict by hand, and nobody hunts for lag by hand: point mmt at a mod and within about a minute it says what is causing the lag and the known way to make it faster, and makes the change itself wherever it can prove the mod still behaves the same. Five goals: test a mod in seconds, port it to any Minecraft version automatically, make modpacks work together, move a project between loaders and platforms, and make any mod faster. Every result is proven in the real game or on a real server.

**71 of 114 steps done.** A step is 🟢 done only when it ran and was checked; the others are 🔵 doing, ⚪ next or ⚫ later, each with a target date. Targets were set on Nov 6, and one that moves keeps its old date.

## Goal 1 — Test a mod in seconds

An author changes code and gets an answer about the mod's real behaviour in seconds, without opening Minecraft: logic tests with no game, the game's own data with no game launched, and a hidden client or a real server with a bot player when the game is needed. Commands: `fast`, `data-check`, `mixin-check`, `ui-check`, `world-check`, `mp-check`, `eval`, `reload`, `plugin-check`, `server-check`.

- **Today:** Logic tests, the game's data and real-game checks all run with no game window. Paper plugins run on a real server with a bot player.
- **The number that says most:** One-file edit, mmt fast, warm is **4 s**, target 4 s (hold) by Nov 27, step 34
- **Also:** Mods with their own behaviour asserted in a real client is **3 mods**, target 4 mods by Dec 4, step 27

**33 · Measure what one game session costs today** (done). Measure RAM, CPU, start time and time per check for one client, one dedicated server and one Paper server, warm and cold, as the baseline the next steps are judged against. *So far:* bench/session_cost.py measures a session from the operating system on Windows, Linux and macOS. This PC is shared, so every point carries how busy it was.

**34 · Every game check with no window** (done). ui-check, world-check, mp-check, eval and the behaviour checks run with no Minecraft window and no sound, with the same assertions and the same 1280x720 captures, and a check stops when a window asked to stay hidden is not. *So far:* ui-check, world-check, eval and mp-check ran with the game hidden and quiet: no game window was on screen after any of 15 warm checks, nor at any half-second sample through a whole mp-check (its client and its own server), and each check kept its assertions and its 1280x720 framebuffer capture. The behaviour checks (AppleSkin's HUD estimate, Zombie Apocalypse's AI) ran hidden on a Linux machine with no screen at all. A check stops when a game asked to stay hidden reports its window library was not rewritten. The title screen no longer costs a fixed 4.5 s wait; it waits only while it fades in. The warm screen check (3.9 s) and scenario (5.1 s) are timed as the whole mmt command; the 1.5 s and 2.9 s of October were the older Windows lane's own loop with a window, so they are not the same work.

**35 · Check the game's data without launching it** (done). A check that needs the game's data but not its picture runs the game's own code with no window and no world: data-check reads what the mod registered, each item as a real stack, and every error the game logs while it loads the data packs. It costs about 5 CPU-s per check once one loaded JVM answers many checks, instead of 49 for a hidden client. *So far:* mmt data-check works on Fabric 26.3: on the Prism Lab demo mod it lists the mod's items, blocks, loot table and recipe with no game launched, and a broken recipe fails it with the game's own error. The game stays loaded: a changed data file costs about 2 CPU-s in 2 s, copied from src without Gradle when Gradle would copy it as it is. A spare game waits behind it, started up to just before the mods' own code, and takes changed code for about 5 CPU-s in 4 s; a changed mixin or loader file loads a fresh game, 12 s. The build is read once and kept until a build file changes. A loaded game holds about 0.38 GB.

**36 · Many sessions at once on one PC** (done). mmt runs at least 8 game checks side by side on this PC, each with its own game folder, without running out of memory, and a waiting hidden client costs almost no CPU. *So far:* 8 projects (copies of the demo mod) each ran data-check at once: from no game all passed within 26.6 s, about 21 CPU-s each and 4.5 GB at the peak; with their games loaded, all passed again within 6.3 s. The 8 loaded games hold 2.85 GB and their 8 spares 2.41 GB. A brand-new project's first check takes about 36 s, 21 of it Gradle reading the build and recording the launch. A hidden game nobody has asked anything for 2 s now draws 10 frames a second, woken at once by the next request: it uses 0.04 to 0.06 cores while waiting instead of 0.14 to 0.16, measured alternately on the same PC, with warm checks as fast as before. Tried and not used: Java's start-up cache for Paper (AOT) halves a start's CPU (48 to 24 CPU-s) but recording it adds about 95 s to one start and its shutdown, and the self-updating class archive saves 2 to 5 s per start but adds about 40 s to the first, a slow first start this step exists to avoid. The faster-start targets set on Nov 6 (a hidden client on 25 CPU-s, a cold check under 10 s, a server start of 10 s) were dropped on Nov 7: they do not move the goal, and their numbers stay as facts.

## Goal 2 — Port a mod to any Minecraft version

One command moves a mod's source from any version to any other, forward or back, with no hand edits, and the result is checked in the real game. Every edit can be undone; what cannot be ported is named, never guessed or dropped. Commands: `port`, `explain`, `dependencies`.

- **Today:** Fabric and NeoForge mods as .jar or source, any version from 1.14.4 to 26.3, in about ten seconds a jar. What comes back working is the gap: of the 150 most-downloaded mods of the most-used release (Fabric 1.20.1, NeoForge 1.21.1), ported as jars to the newest game and linked against it, 11 of 294 link. One update at a time, 36% link across the 35 big updates and 93% across the 29 small ones (62% together). What does not link is named, never guessed. 16 of the 126 corpus ports build with no hand edits.
- **The number that says most:** Mods that go to any version: the ported jar links on every release, forward and back, Fabric and NeoForge is **9 mods** ([what is not there yet](scoreboard/any-version.md))
- **Also:** Breaks left before every mod goes to any version: each type of break holding a mod on some release, one per mod is **8,524 pairs** ([what is not there yet](scoreboard/any-version.md))
- **Also:** Mods that go to any version from source: mmt port builds them with no hand edits and the built jar links on every release, forward and back, Fabric and NeoForge is **not measured** ([what is not there yet](scoreboard/source-any-version.md))
- **Also:** Mods of the most-used release whose ported jar links on the newest game, Fabric and NeoForge is **27 mods**
- **Also:** Most-downloaded mods whose ported jar links, the big updates only, Fabric and NeoForge is **2,613 mods**
- **Also:** Corpus ports that build with no hand edits is **16 updates**, target 60 updates by Dec 22, step 44
- **Also:** Real mods with a port that works in the game is **9 mods**, target 6 mods by Dec 18, step 12

**81 · Say how to fix it, from fixes that already worked** (later). Every cause named in step 80 comes with the known way to make it faster: what to change, the mod it worked on and the gain measured there. Today 14 patterns exist, each written from one accepted speedup, and nobody has checked how often they match a mod they were not written on. The step measures that on mods held out from the pattern library, and grows the library by the kind of slowness (the game call misused, the cache dropped, the work repeated every tick), ranked by how many of the most-downloaded mods show it, never by one mod's profile.

**82 · Make the fix automatically and prove it** (later). The part Jon wants most. A pattern today is advice for a person. Here a pattern also carries the edit, written once by an agent as a tested rule the way a port rule is, and applied by mmt with no AI call. One command finds the slow spot, makes the edit, and runs the proof perf-optimize already does: baseline and changed mod in alternating fresh games, every behaviour gate passing, the speedup interval above 1. The change is kept only when that passes and can be undone; when it does not pass, mmt says so and leaves the mod as it was. Behaviour gates are written by hand per mod today, so this step also needs them made for any mod (the behaviour fingerprint is the starting point).
